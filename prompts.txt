Prompts, Thoughts, & Verdicts
Quest1 Take-Home — "Find the Exact Frame Where a Dialogue Appears in a Video"

Building a system that finds one specific moment inside an hour-long
video isn't a single-shot task. The problem statement itself contains a
genuine ambiguity: "on-screen dialogue" could mean visible caption text,
or it could be film terminology for a character speaking on camera —
which says nothing about text at all. I didn't resolve that by guessing.
I resolved it by building both paths, running them against the real
video, and letting the evidence decide.

Below is the actual sequence of prompts, dead ends, real bugs, and
verdicts that got me there.

---

Phase 1: Understanding the Problem & the Brute-Force Dilemma

The first thing that mattered wasn't the algorithm — it was reading the
constraints correctly. No manual inspection allowed. The evaluators
might swap the video or the phrase. That second constraint alone ruled
out any shortcut tuned to one specific file.

Prompt 1: "Here's the problem statement — help me solve this step by
step, keeping the earlier requirements in mind."

Prompt 2: "Walk me through Phase 1. I want to understand it properly and
prepare rigorously — what algorithms are actually being used here,
explain in depth."

The Result: A coarse-to-fine search design — sample sparsely first to
find the approximate region cheaply, then refine only within that small
window to get frame-accurate precision. A ~54-minute, 78,204-frame video
at 1fps sampling only touches ~3,258 frames in the coarse pass instead
of all of them.

The Thought: I specifically asked why not binary search instead of
linear sampling. The answer mattered — binary search needs a monotonic
predicate, and caption presence isn't monotonic (the phrase could appear
once, many times, or never). So this is a reduced-rate linear scan, not
a disguised binary search — an important distinction to be able to
defend, not just a detail.

---

Phase 2: Fuzzy Matching & the Threshold That Was Wrong on the First Try

OCR output on real video is noisy, so exact string comparison was never
going to work. I went with rapidfuzz's partial-ratio scoring instead.

The Result: A working matcher — but my own assumption about how it would
behave turned out to be wrong. I assumed unrelated text would score
near 0. The test suite proved that false — unrelated text actually
scored in the ~40s-50s range with partial_ratio. That's the real reason
MATCH_THRESHOLD ended up at 80 with genuine headroom above that floor,
not a number that just felt safe.

The Verdict: Trust the test, not the assumption. This became a pattern
for the rest of the project.

---

Phase 3: First Real Run — Performance, and a False Positive That Looked
Real

Prompt 3: "I want the whole thing working now, using the actual video
link as input. What do I do?"

Running it for real surfaced two separate problems, not one.

First: the coarse scan on a 54-minute video produced zero output for
minutes and looked completely frozen. Not broken — just silent, with no
way to tell the difference.

The Fix: Progress reporting (elapsed time, ETA, running best score) plus
an actual speed fix once I looked at where the time was going: downscale
frames before OCR, and switch Tesseract to sparse-text mode since a
video frame isn't a structured document page.

Second, and more serious: the fixed version returned a "match" at 100%
confidence. I looked at the actual extracted text instead of trusting
the number — it was "t\\". Obviously nothing.

Prompt 4: Flagged this directly rather than re-running and hoping it was
a fluke — asked why a single garbage character could score as a perfect
match.

The Result: Root-caused it — rapidfuzz's partial_ratio slides the
SHORTER string across the longer one, so a 1-character fragment can
trivially "fully match" almost anything. Fixed with a minimum-length
guard before any score is trusted at all, plus a regression test that
locks this exact failure down.

---

Phase 4: The Clean Negative, and Questioning My Own Assumption

Once both bugs above were fixed, I ran the complete OCR pipeline against
the real video end to end. No crash. No false positive. But also no
match anywhere — the best score across the ENTIRE video was ~59, well
under threshold, and every top candidate was OCR reading film grain
noise, not real text.

Prompt 5: "There can't actually be text on screen, can there? Read the
problem statement carefully again."

The Result: Went back and reread "on-screen dialogue" properly — it's
genuine film terminology that can mean a character speaking while
visible in frame, not necessarily displayed text at all. Given the clean
negative OCR result, that reading suddenly made far more sense than my
original literal one.

The Verdict: A negative result isn't a failure state — it's evidence.
Built the audio fallback because the evidence pointed there, not as a
speculative hedge.

---

Phase 5: The Audio Path, and a Confirmed Result

Built asr_utils.py — extract audio, transcribe with faster-whisper,
reuse the SAME matching function already used for OCR rather than invent
a second one. Wired --mode auto so OCR runs first across the whole
video, and only falls back to audio if OCR found nothing confident —
the same order I'd have investigated it myself.

Ran it directly against the real video. Got a genuine match: 92.86%
confidence, timestamp 00:05:21, text transcribed as "My mind rebels its
stagnation" — Whisper misheard "at" as "its."

The Verdict: That mishearing is actually the strongest evidence for why
fuzzy matching was the right call from the very start — an exact-match
approach would have missed this true positive outright. Also explicitly
kept OCR as the default first path even after this confirmed result,
since a different evaluation video might genuinely have the phrase as
visible text — this result validates having both detectors, it doesn't
retire the one that didn't fire here.

---

Phase 6: Precision — the Timestamp Wasn't Actually Exact

Prompt 6: "Is my approach right?"

Asking that instead of accepting the working result is what surfaced a
real gap: the ASR timestamp was accurate to the start of the whole
spoken SEGMENT, which could include several unrelated seconds before the
target phrase actually began. Not literally "the exact frame."

The Fix: Added word-level timestamps and a genuine coarse (segment) →
refine (word span) structure for the audio path, mirroring the OCR
path's own design.

Building that turned up a second real bug: the word-span comparison was
reusing the same scoring function as before, and that function rewards
partial matches — so an incomplete phrase (missing its last word) could
score just as well as the complete one. Had to write a second, genuinely
different comparison function specifically for this case, with a test
proving the two behave differently.

---

Phase 7: The Correctness Gap Hiding Inside an "Optimization" Request

Prompt 7: "Give me ideas to make this stand out — I want a genuinely
unique approach here, something that will actually impress them."

The Result: What actually held up wasn't a flashy new algorithm — it was
realizing my OWN original code had a real bug. Both search paths scanned
the ENTIRE video/audio and returned whichever candidate scored highest
overall. But the spec asks for the FIRST occurrence, not the
best-scoring one. If the phrase occurred twice and a later instance
happened to score marginally higher, the original logic would have
silently returned the wrong one.

The Fix: Since both scans proceed chronologically, stopping at the first
sample/segment that crosses threshold guarantees the TRUE first
occurrence — faster and more correct in the same change, not a
trade-off between the two. Applied it to both OCR and audio paths, since
the same bug existed in both places identically.

---

Phase 8: Optimizing Speed Without Quietly Breaking Correctness

Prompt 8: "Optimize the whole solution properly."

Two real things came out of actually looking at where time was going:
frame reading was re-seeking the video on every single sample, which is
genuinely expensive on compressed video — switched to one seek plus
sequential reading forward. And since Tesseract runs as its own
subprocess, OCR calls could run in real parallel across a batch of
frames without fighting Python's GIL.

The Dilemma: Processing frames out of order inside a batch could let a
later frame "win" if it happened to finish OCR first — quietly undoing
the early-exit correctness fix from Phase 7.

The Verdict: Used order-preserving batch processing so results are
always scanned chronologically within a batch, and batches themselves
run strictly in sequence. Wrote a dedicated test — an earlier weak match
and a later strong one — proving the earlier one still wins even with
parallel OCR running underneath.

---

Phase 9: OCR vs. an Actual Vision Model

Talked through why a vision-LLM genuinely beats plain OCR here —
Tesseract has zero semantic understanding of what it's reading, which is
exactly why the Phase 3 false positive was possible at all. A model that
can actually reason about whether text is really present closes that gap
at the source.

The Dilemma: Running a vision-LLM on every sampled frame across a whole
video would be slow and needlessly expensive.

The Verdict: Hybrid, tiered design — OCR still does the full, free scan
across the whole video exactly as before. The vision-LLM only verifies a
small shortlist of OCR's top candidates (top-K, bounded regardless of
video length), and — same principle as Phase 7 — that shortlist gets
re-sorted to chronological order before checking, so a later candidate
with a marginally higher OCR score can't jump the queue over a genuinely
earlier one the LLM actually confirms. Kept strictly opt-in, since it
needs an API key and costs real money per call.

---

Phase 10: Containerization & the Limits of What's Fixable in Code

Asked to containerize the whole thing. The image itself built cleanly
once a real, unrelated problem was sorted — the network was corrupting
package downloads mid-install, fixed with retry-with-backoff logic in
the Dockerfile.

Getting a full run INSIDE the container was a much longer fight than any
of the code itself. Repeated network failures reaching the video source
specifically — a fake certificate mid-connection, connections cutting
out mid-download, the source flatly refusing the request. Tried
switching networks, tried an older-style TLS handshake, tried making the
request look more like a real browser. Eventually confirmed the video
played completely fine in an actual browser on the same network — which
at least proved this wasn't a real block on the source, just something
about script-based requests specifically getting caught in the middle.

The Verdict: Stopped once it was clear the image built and ran correctly,
and the container reached the exact same execution point as the version
running outside Docker. The failure was consistently external, not
anything in the container or the code — and I'd rather say that plainly
than pretend a live run succeeded when it didn't.

---

Phase 11: Catching My Own Mistakes Before Submitting

Two things I caught myself, not from an error message:

Prompt 9: "Didn't the brief say not to manually inspect the video to
find the answer? I want to make sure opening it earlier to debug the
download issue doesn't count against that — can you check?"

The Result: It didn't — the actual timestamp came entirely from the
program's audio search, not from me watching and noting anything. Still
wanted to verify that directly instead of assuming it was fine.

Prompt 10: "Why is the commit history showing a different name than my
GitHub account? I don't want to submit this with the wrong contributor
showing."

The Result: A real attribution problem from a leftover git identity on
a shared machine. Reconfigured it and rewrote the commit history so
every commit correctly links back to my actual account before
submitting.

---

Phase 12: Closing the Untested Gap — a Synthetic Video

By this point I had real, verified evidence for an OCR NEGATIVE (the
actual video) and an ASR POSITIVE (the actual video) — but the
OCR-POSITIVE path, actually detecting real on-screen text, had never
been exercised against real data, only mocked in unit tests.

Prompt 11: "Give me a new video to test the OCR side with."

The Dilemma: I can't verify what's actually in a third-party video
without watching it myself, and handing over an unverified guess would
be worse than not testing at all.

The Verdict: Generated a small, fully controlled local test video
instead — known text, visible only in a known time window, nothing
uncertain about it. Ran the pipeline against it directly, bypassing the
network entirely.

The Result: A genuine, correct detection — right frame, right
timestamp, fuzzy-matched extracted text at 84% confidence, early exit
firing correctly. First real, non-mocked confirmation that the OCR path
correctly detects genuine on-screen text, not just correctly detects its
absence.

---

Looking back at the whole arc: almost none of the real progress came
from getting something right on the first try. It came from running
things against real data, taking results seriously enough to question
them instead of accepting a working-looking answer, and fixing whatever
that turned up — twice on real bugs, once on a wrong assumption, and
once on a correctness gap hiding inside what started as a speed request.
That's the actual skill this problem was testing for.
