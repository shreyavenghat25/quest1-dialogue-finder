prompts.txt — how this actually came together
================================================

Every prompt I actually used with Claude while building this, kept
honest — including the parts where my first idea turned out wrong. This
file gets checked against the real solution, so it needs to hold up if
I'm asked about any specific decision in it.

STARTING OUT

I shared the Quest1 talk screenshots as they came in live — the partner
ecosystem tiers, the "Why Quest1" pitch, the campus offer numbers, the
testimonials, the placement process, the submission requirements — and
asked for them to be turned into proper notes as I went.

Once the actual problem statement PDF dropped ("Find the Exact Frame
Where a Dialogue Appears in a Video"), I asked for help solving it step
by step, and specifically asked to keep the extra requirements from the
talk in mind — documentation, extensibility, the bit about evaluators
being able to tell when something's polished but not actually understood.

Asked for unit tests to be treated as a hard requirement from day one,
not an afterthought. Asked for the README to include a real summary of
what's in the repo, not just a title.

What came out of this first stretch: the two-phase coarse-scan-then-
refine design, split across solve.py / video_utils.py / ocr_utils.py /
match_utils.py, and fuzzy matching via rapidfuzz instead of exact string
comparison. Worth flagging — my first assumption that unrelated text
would score near 0 was just wrong. The test suite caught it (turned out
to be ~48, not ~0), which is actually why the threshold ended up at 80
with real headroom, not some number that just felt safe.

---

FIRST REAL RUN

Ran it against the actual video for the first time. It's about 54
minutes — 78,204 frames. The coarse scan just sat there with zero output
for ages, looked completely frozen. Asked for help telling the difference
between "broken" and "just slow," and asked for the script itself to be
fixed so I wouldn't hit this blind again.

Got progress reporting out of that (elapsed time, ETA, running best
score), plus an actual performance fix once we dug into why it was slow:
downscaling frames before OCR and switching Tesseract's page-segmentation
mode, since a video frame isn't a structured document.

---

THE FALSE POSITIVE

Ran the fixed version. Got a "match" back at 100% confidence. Looked at
the actual extracted text — it was "t\\". Obviously nothing. Flagged it
instead of just re-running and hoping.

Traced it down to how rapidfuzz's partial-ratio scoring actually works —
a tiny fragment can trivially "fully match" inside almost anything, so a
single stray character was enough to fake a perfect score. Fixed with a
minimum-length check before trusting any score at all, and added a test
that locks this exact failure down so it can't quietly come back.

Also picked up a smaller but real fix here: stop re-downloading the
~1GB video every single run when it's already sitting on disk.

---

THE CLEAN NEGATIVE

Ran the whole fixed pipeline end to end. No crash, no false positives —
but the best score anywhere in the entire video was around 59, well
under threshold, and every top "candidate" was just OCR reading noise
off the film grain. Asked what that actually meant, tying it back to the
earlier question of whether this was really on-screen text at all.

That clean negative is what justified building the audio path — not as
a hedge "just in case," but because the evidence was already pointing
that way. Built asr_utils.py (audio extraction + Whisper transcription),
wired up asr_scan() to reuse the SAME matching function already used for
OCR rather than invent a second one, and set up --mode auto so OCR runs
first and only falls back to audio if it comes back empty — basically
how I'd have investigated it myself by hand.

---

THE REAL RESULT

Ran the audio path directly against the real video. Got a genuine match
this time — 92.86% confidence, timestamp 00:05:21, the phrase itself
transcribed as "My mind rebels its stagnation" (Whisper misheard "at" as
"its," a small but real ASR slip).

That confirmed with actual evidence, not a guess, that the dialogue in
this video is spoken rather than displayed. Wrote that into APPROACH.md
honestly, including the "at" vs "its" detail, since it's a direct,
concrete reason fuzzy matching was the right call from the start — an
exact-match approach would've missed this outright. Also made a point of
noting that OCR-first-then-ASR-fallback still makes sense as the default,
since a different evaluation video might actually have the phrase as
visible text — this result validates having both paths, it doesn't
retire the first one.

---

MAKING IT ACTUALLY PRECISE

Went back and looked at what I had more critically. The timestamp I was
getting was for the start of the whole spoken segment, which could
include several unrelated seconds before the actual phrase. Not really
"the exact frame." Asked for that gap to be closed.

That meant adding word-level timestamps and building a proper
coarse-then-refine structure for the audio path too — segment-level
first, then narrow down to the exact word span. Building that turned up
a second real bug: the word-level comparison was reusing the same
scoring function as before, and that function doesn't penalize an
incomplete match, so a phrase missing its last word could score just as
well as the complete one. Had to write a second, different comparison
specifically for this case, with a test proving the two actually behave
differently.

---

TRYING TO STAND OUT

Asked directly for ideas that would make the project stand out, and
picked early-exit as the one to actually build.

What actually came out of that conversation wasn't a flashy new
technique — it was realizing my own original code had a real,
non-obvious bug: it scanned the WHOLE video and returned whichever
candidate scored highest overall, but the brief asks for the FIRST
occurrence, not the best-scoring one. If the phrase ever showed up twice
and a later instance happened to score a touch higher, the old logic
would've quietly returned the wrong one.

Fixed it on both the OCR and audio paths at once, since the same problem
existed in both places — stop at the first thing that crosses the
confidence bar, since both searches move through the video in time order
anyway. That's faster AND it closes the correctness gap in the same
change, not a tradeoff between the two. Added a flag to disable it for
the rare case where the full ranked list is actually wanted, and tests
proving it fires correctly and can be turned off.

---

Looking back at the whole thing, almost none of the real progress came
from getting something right on the first try. It came from actually
running things against the real video, taking the output seriously
enough to question it instead of just accepting a working-looking
result, and then fixing whatever that turned up. The two real bugs and
the wrong first assumption are honestly the strongest part of this —
not because bugs are good, but because finding and fixing them is the
whole point of what's being evaluated here.
